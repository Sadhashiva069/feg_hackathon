# Compliance note — Challenge 3, Game Load Time (PSK track)

One page mapping the design to the EU baseline and the responsible-gambling (RG) rules in the FEG *EU & Croatia Regulatory Compliance Guide* (4 Sep 2026). Awareness-level, for a hackathon proof of concept; not legal advice. The items under *Before production* are the review points we would hand to FEG Legal & Compliance.

## What the prototype is, in compliance terms

A lobby shell, a service worker and an edge configuration that make a **certified, unmodified** game start faster by paying its load cost earlier (consented pre-load of one predicted game) and elsewhere (edge compression and immutable caching). It touches no game logic, no payments, no onboarding. The only personal-data-like inputs are **synthetic player ids** in the sandbox and the **hashed sample event log** used offline to measure prediction accuracy. No live feed or production API is called: the bundle is the offline build and the sandbox never contacts the provider's game server.

## Requirement → design

| Requirement | How the design meets it | Where |
|---|---|---|
| **Certified package unaltered** (challenge guardrail) | Served byte for byte from a versioned, immutable path. SHA-256 of all 379 files is checked by `node tests/verify-bundle.js`. Pre-boot and park use the two hooks the bundle itself exposes (`stopPixiApp` / `startPixiApp`); the game's own splash and Play button are never auto-clicked, so the provider's flow is untouched. | `src/edge/server.js`, `tests/`, `src/lobby/app.js` (`park`, `reveal`) |
| **RG interstitials, reality checks, session limits, age gates at full fidelity** | One gate function decides on **every** path: before a game is opened, before anything is pre-loaded, and before a hidden pre-boot starts. Self-exclusion and age verification are modelled as a **register check** (Croatian Act on Games of Chance pattern), not a checkbox. Reality check every *N* minutes with two **equally weighted** choices. **Session limit** is a hard stop: the game is closed and the pre-loaded copy is discarded the moment the limit is reached. A player who may not play never has a game warming in the background. | `app.js`: `rgVerdict`, `applyConsent`, `warmBoot`, `launch`, `rcTick`, `showRealityCheck`, `showSessionLimit` |
| **No dark patterns** | The accelerator is invisible to the player: no "ready" badge, countdown, urgency or auto-start in the player view (the "ready" marker exists only in the collapsed instrumentation panel used for the demo). Speed removes friction between *choosing* and *playing*; it never nudges toward *continuing* or *spending*. | `index.html` (instrumentation `<details>`), `readyBadge` |
| **No inducements to vulnerable or self-excluded customers; 18+ throughout** | The prediction is used **only to decide what to cache**, never for offers, ranking, push or marketing. It is disabled for excluded, unverified and over-limit accounts. The 18+ register check runs at the lobby entry point (chip + banner), at launch, at pre-load and at reveal. | `applyPlayer`, `rgBanner`, `rgVerdict` |
| **GDPR** (lawful basis, minimisation, privacy by design, Art. 25) | On the device: the files of one predicted game (up to three kept, evicted LRU) and the id of the last game opened, both **only while the pre-load switch is on** and both removed by "Clear stored files" or by switching the pre-load off. Measurement beacons carry a synthetic player id, timings and a truncated user agent; the edge log never stores a client address (a short hash keys the per-client link profile). The predictor is a count-based model over the **same `casino_game_launch` events the platform already collects**; per-player state is the last three games. Profiling here has no legal or similarly significant effect, but it is profiling: a DPIA screening is listed below. | `sw.js`, `app.js` (`finishLaunch`, `onConsent`, `clearCache`), `server.js` (`anon`), `src/predict/build.js` |
| **ePrivacy** (Dir. 2002/58/EC Art. 5(3), terminal-equipment storage) | Two cases are kept apart. (1) Caching the files of a game the player **explicitly opened** is strictly necessary for the requested service, like the browser's own HTTP cache: no consent needed. (2) **Predictive pre-load** of a game the player has not asked for is not strictly necessary: the position taken here is that it is a **technical cache for the service the player is already using** (the casino lobby), in the same class as the browser's HTTP cache, `<link rel="prefetch">` or a CDN warming its edge: it stores only the game's own public files, bounded (≤ 25 MB per game, three games, LRU), evictable, and nothing about the player leaves the device to decide it (the last game id stays local). It is therefore **on by default** and the lobby offers a plain-words switch as a player preference (off = nothing is fetched ahead of a tap, stored files are cleared, the choice is remembered), not as a consent gate. This reading of the "strictly necessary" exemption is the item flagged for FEG Legal & Compliance review before production, as the guide requires for any real build; if Legal reads Art. 5(3) the other way, `PRELOAD_DEFAULT_ON = false` in `src/lobby/app.js` turns the same switch into an unticked opt-in. No marketing, push or notification flow exists. | `index.html` (consent label + note), `applyConsent`, `savePlan` |
| **AMLD / KYC, eIDAS 2.0** | Out of scope for this feature; the gate consumes the account's verification status as an attribute ("over 18: yes/no") in the way an EUDI-Wallet attribute proof would supply it. The prototype never sees identity documents. | `VERIFIED` register (synthetic) |
| **EU AI Act** | The next-game predictor is a minimal-risk statistical model (transition counts, per-player affinity, popularity). It is not used to influence the player's choice, only the cache; it is transparent in the UI ("Predicted next … because …"); it is switched off for at-risk accounts and without consent. Should FEG later use it to **order** the lobby, it becomes a recommender system and DSA Art. 27 transparency applies. | `predict()`, `build.js` |
| **Accessibility (EAA / WCAG 2.1 AA)** | Real buttons for tiles (Enter launches), `aria-label`s, `role="dialog"` with `aria-modal`, initial focus and a Tab trap on modals, visible focus rings, `role="status"` banners and toasts, text tokens at ≥ 4.5:1 contrast on the dark ground, `prefers-reduced-motion` respected, 44 px modal targets. The game canvas itself is the provider's. | `index.html`, `modalKey` |
| **Anonymised / sample data only** | `data/` is git-ignored; the derived model (`var/`) is git-ignored; the sandbox lobby uses synthetic player ids; walkthrough videos and event logs were used only offline. | `.gitignore`, `README.md` |
| **Security hygiene (NIS2 awareness)** | No secrets in the repository (`.env.example` is empty of values), path-normalised file serving, `nosniff`, worker scope limited to `/games/*`, transient 5xx retried so the engine never sees an edge error, no production system touched. | `server.js`, `sw.js` |

## Before production (hand-over items)

1. **DPIA screening** for the per-player prediction (profiling, low impact) and a retention rule for launch beacons.
2. **Provider confirmation** that a game parked at its own Play button (engine ticker stopped, no reels) opens no game session, no RNG round and no bet, so a pre-booted game is not "play" under the Croatian rules. The sandbox build is offline, so this is asserted from the engine's code paths, not verified against a live game server.
3. **Consent record** stored server-side against the account (today it is a per-player key on the device) and shown in Account › Privacy.
4. **WCAG 2.1 AA audit** of the production lobby; the prototype covers the basics only.
5. **DSA check** if the prediction is ever used for lobby ordering or promotions (it is not, in this design).
6. **Legal read** of the ePrivacy classification above (explicit-launch caching = strictly necessary).
